  Even with the correct password, Prisma's schema/query engines (Rust

  ROOT CAUSE OF BLOCKER B: Prisma's Rust engine resolves DNS
  independently from libpq. On this machine, the pooler hostname's DNS
  returns IPv4-mapped IPv6 addresses (::ffff:18.x.x.x) which Prisma's
  engine intermittently attempts to connect over IPv6. The host has no
  real IPv6 route to the pooler, causing the TCP connect to time out
  after ~5s, which Prisma reports as P1001.

  PROOF: Replacing the hostname with its IPv4 literal in DATABASE_URL
  reduced failures from ~10-20% to 0%. Tested across 20+ iterations on
  each IP literal — zero failures. psql never fails with either.

6. WHY psql WORKS BUT PRISMA DOESN'T (IPv6 detail)
----------------------------------------------------
psql uses libpq which uses glibc's getaddrinfo. On this machine,
getaddrinfo with AF_INET (IPv4) returns working addresses directly.
Prisma's Rust engine uses its own DNS resolution (via the `hickory-res`
or `trust-dns` stack) which queries for both A and AAAA records. The
AAAA lookup returns IPv4-mapped IPv6 addresses (::ffff:18.x.x.x).
When Prisma tries to connect via an IPv6 socket to these mapped
addresses, the kernel's IPv6 routing has no default route (only
link-local fe80::/64), so the connect attempt hangs until timeout.
The IPv4 literal bypasses DNS entirely, avoiding this path.

LONG-TERM FIX OPTIONS:
  - Upgrade Prisma (newer versions may fix IPv6 socket selection)
  - Configure sysctl to disable IPv6 on non-loopback interfaces:
      sysctl -w net.ipv6.conf.all.disable_ipv6=1
  - Use a DNS name that only has A records (if Supabase offers one)
  - Keep the IPv4-literal approach with runtime getent in push.sh

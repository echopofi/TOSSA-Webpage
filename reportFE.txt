## 0. Route protection (auth guard) — DONE
- **Problem fixed:** /dashboard, /payments, /elections, /admin rendered with no
  login check; /admin had no non-admin redirect. Anyone could open the page shell.
- **Approach:** client-side guard (NOT middleware.ts). Sessions live in
  localStorage (no auth cookie yet), and middleware can't read localStorage —
  so `components/auth/AuthGuard.tsx` (a `useSyncExternalStore` client component)
  wraps the ENTIRE layout of each protected route and renders nothing but a
  spinner until the session is confirmed:
  - no session → `router.replace("/login?next=<original-url>")`
  - session, not admin on /admin → `router.replace("/dashboard")`
  - both guards render a spinner while redirecting; data calls never pre-empt it.
  - `lib/session.ts` now exposes `subscribeAuth`/`getCurrentUserSnapshot` (for the
    guard + Navbar) and keeps a cached snapshot; also syncs across tabs.
- **Login actually creates a session now:** previously `apiLogin` never called
  `saveCurrentUser`, so "logged in" users had no session to check. Login now
  persists {full_name, email, role} and honors the `?next=` return param
  (relative-only, no open redirects). Fresh register also stores `role: "member"`.
- **Admin identity:** mock `apiLogin` returns `role:"admin"` for
  `admin@alumni.ng` (any password) so the guard path can be verified end-to-end;
  `apiMe` maps session role onto the AuthUser.
- **/exco now public:** replaced the sidebar/auth layout with a public-navbar
  layout (no guard) — matches the landing + navbar link. Landing, /sets, /login,
  /register untouched. /members/[id] stays public via the root layout.
- **Backend:** no changes needed — API-level auth already rejects unauthed/non-admin
  calls; this was purely a frontend rendering gate.
- **FOUND + FIXED a hydration race in AuthGuard:** during React hydration the
  component commits with the SSR snapshot (null), so the very first effect
  redirected logged-in users to /login?next=… before the real localStorage
  snapshot was applied (verified live in headless Chrome: session present yet
  bounced to /login). Fixed by gating the redirect on a `useHydrated()` flag
  (useSyncExternalStore, server snapshot = false) — no setState-in-effect.
  Re-verified: logged-out /id-card → /login?next=… (content not shown), logged-in
  → card renders, member on /admin → /dashboard.
- **Future:** when the real backend issues an httpOnly auth cookie, add
  `middleware.ts` (cookie presence check) plus a server-side `GET /api/auth/me`
  call in each protected layout; keep AuthGuard as the defensive client layer.

## 6. REAL photo upload — verified, with one blocker raised
- **Found:** `frontend/.env.local` did not exist, so `NEXT_PUBLIC_API_URL` was
  unset → `isRealBackend()` was false → the canvas/data-URL MOCK path was firing
  for every registration upload. This is why photos looked "local".
- **Fixed:** created `frontend/.env.local` (`NEXT_PUBLIC_API_URL=http://localhost:3000`)
  + added `frontend/.env.local.example`; restarted `next dev -p 3001` so the var
  is inlined (confirmed the bundle now carries the URL, and `undefined/api/sets`
  is gone — /sets now reads the real backend). `.env*` is gitignored (by design).
- With the env in place, `uploadMemberPhoto()` uses the real path: POST
  /api/upload/cloudinary-signature → unsigned upload to Cloudinary → `secure_url`.
- **Verified live against the running backend:**
  - signature endpoint returns real signed params (no secret shipped) ✅
  - **upload works end-to-end** with the real cloud name (`q52frkzl` in
    backend/.env): unsigned upload → HTTP 200 → real `secure_url`
    (https://res.cloudinary.com/q52frkzl/...), stored in `members.profile_image` ✅
  - DB persistence confirmed via a throwaway registration: `profileImage` landed
    in `members.profile_image` (queried, user deleted) ✅
- **Photo upload behavior:** real Cloudinary path is now used; if the signature
  or upload ever fails (e.g. bad cloud name), the client falls back to a resized
  local data URL + `console.warn` ("Cloudinary upload unavailable …") so
  registration still completes. Previously this was "root" blocked / failed
  loudly; the fallback is intentional.
- **Integration heads-up:** backend returns `profileImage` (camelCase); frontend
  Member uses `profile_image`. The mock layer maps today; real fetches need the
  same mapping or the ID card shows initials.
